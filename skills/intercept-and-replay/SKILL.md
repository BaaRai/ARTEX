# Intercept, edit, replay

The Repeater-equivalent for this platform. Use it whenever the interesting request is generated by JavaScript, signed by the client, or must be re-sent with one field changed — and for proving access-control findings that need two identities and byte-identical replays.

mitmproxy 12+/mitmdump is installed; the platform also runs a capture proxy on `127.0.0.1:8788` that Bash `curl`/`wget` and python-requests already use automatically (env `http_proxy`/`https_proxy`, CA at `/app/data/traffic/_ca/mitmproxy-ca-cert.pem`). Raw scanners bypass it — that is why their rate flags still matter.

Quiet profile applies: one request in flight, ≤2 req/s. Replay loops are where the rate gets violated — sleep between iterations.

## 1. Get the request

**From the browser (preferred for JS-generated calls).** Drive the page with the browser MCP, read `browser_network_requests`, and pull the exact request (method, path, headers, body) for the call you care about. Then reproduce it with `curl` so it is file-backed and editable.

**From a flow file.** Capture live traffic and filter:

```
mitmdump -p 8899 -w /app/data/sessions/conv-62/flows.mitm
# then, in another shell, drive the app through 127.0.0.1:8899
mitmdump -nr flows.mitm --flow-detail 3 "~u /api/" > api-calls.txt
```

`-nr` = read, no listen. `--flow-detail 3` prints request and response bodies. Narrow with a filter expression before dumping: `~u <path>`, `~m POST`, `~hs <header>`.

**From devtools copy-as-curl.** Paste into a file, then normalise: replace the absolute origin with `{host}`-style variables, one header per line.

## 2. Replay a single request

Bodies are sent from a file so binary and JSON survive:

```
curl -sS -D hdr.txt -o body.bin \
  -X POST "https://{host}/api/x" \
  -H @hdrs.txt \
  --data-binary @req.json
```

- Drop hop-by-hop headers (`Connection`, `Content-Length` when curl recomputes, `Accept-Encoding` when you need readable bodies).
- Keep `Cookie`, `Authorization`, `X-CSRF-*` byte-identical for a pure replay; for a modified replay regenerate the CSRF value from the page or a prior call.
- Compare with `diff <(jq -S . old.json) <(jq -S . new.json)` rather than eyeballing, and keep the two responses as evidence files.

## 3. Modify precisely

- **One variable per run.** Changing three fields at once and getting 403 tells you nothing.
- Access-control tests: replay identity A's request with identity B's cookie — same URL, same body, zero other changes. Then repeat with no cookie at all (BFLA) and with a lower-privilege role.
- Type juggling: `"1"` → `1` → `["1"]` → `null`; drop a field entirely; duplicate it in the JSON; send it in the query instead of the body.
- Method/verb: `GET`↔`POST`, `PUT`↔`PATCH`, `POST` with `X-HTTP-Method-Override: PUT`.
- Host/forwarding: `X-Forwarded-Host`, `X-Original-URL`, `X-Rewrite-URL` for path-normalisation bugs.

## 4. Scripted replay (multi-step or parameterised)

A `replay.py` addon is more honest than a shell loop when a token must be refreshed between steps:

```python
from mitmproxy import http
def request(flow: http.HTTPFlow):
    flow.request.headers["X-Test"] = "1"
```

```
mitmdump -p 8899 -s replay.py
```

Or replay a saved flow through the server, so curl needs no URL rewriting:

```
mitmdump -nr flows.mitm --server-replay flows.mitm --server-replay-nopop -p 8899
```

`--server-replay-kill-extra` stops unmatched requests from reaching the target — useful when the client fires analytics you do not want to pace.

## 5. Browser through the proxy

Point the browser MCP's context at `http://127.0.0.1:8899`, install the mitmproxy CA, and interact. Server-side replay (step 4) makes the page replay deterministically without touching production twice.

For WebSocket work use `browser_console_messages` plus mitmproxy `ws` flows; the framing is in the flow file.

## 6. Session and token work

- Session fixation: capture `Set-Cookie` on login, log out, log back in, compare values. Rotation is proven by a changed id on every login and by an old id failing.
- Remember-me / refresh tokens: decode the JWT claims offline (`jwt_tool`), then replay after logout to see whether revocation happened.
- CSRF: strip `Origin`/`Referer` and the token on a state-changing request; a 200 with a persisted change proves the gap.

## 7. Evidence rules

- One directory per finding: `NN-identityA.req`, `NN-identityA.resp`, `NN-identityB.req`, `NN-identityB.resp`, plus a `notes.md` naming the single variable changed.
- For BOLA, the killer artefact is identity B's response containing identity A's data with `200`, next to identity A's identical request.
- Attach the flow file segment (`mitmdump -nr flows.mitm "~u /api/x" -w slice.mitm`) when the request had signed headers that curl cannot reproduce.
- Never edit a response file; keep the raw bytes and derive a pretty copy.

## 8. False-positive traps

- Browser clock skew or an expired token makes the "B sees A's data" claim actually a stale-session 200.
- A CDN caching the identity A response and serving it to B — bust with a unique query parameter on both replays.
- Client-side-only redaction: the field is hidden in the UI but present in both responses, so it is not a finding.
- `--server-replay` answering from the file instead of the server (stale by design) — check the `Server-Replay` behaviour before concluding a fix works.
- CORS/preflight: a modified header can trigger preflight and a 200 from the OPTIONS handler, masking the real result — always read the actual method's response.
